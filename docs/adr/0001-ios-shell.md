# ADR 0001 — iOS shell: Capacitor, not Tauri mobile

- **Status:** accepted
- **Date:** 2026-11-01
- **Context:** release on the App Store (iPhone + Mac App Store), one codebase

## Decision

iOS ships with **Capacitor 8** and the existing React/Vite bundle
(`vite build --mode mobile`). The desktop keeps **Tauri 2**: the updater,
signed `.dmg`/NSIS installers and the Rust command `updater_runtime_info`
stay where they already work. The web build is unchanged.

The React application code is shared by all three shells. Only a thin
platform layer differs: `src/platform/*` decides at runtime whether "save a
file" means a download (web), the Tauri save dialog (desktop) or the iOS share
sheet (mobile).

## Why Capacitor

| Criterion | Capacitor 8 | Tauri 2 mobile |
|---|---|---|
| Same UI engine | WKWebView | WKWebView |
| Bundle the app already has | React + Vite | React + Vite + Rust |
| Share sheet | `@capacitor/share` (official) | no official plugin; `tauri-plugin-share` is community, last release 2024 |
| Haptics | `@capacitor/haptics` (official) | `@tauri-apps/plugin-haptics` (official) |
| Local storage | `@capacitor/preferences` + SQLite community | `@tauri-apps/plugin-sql` (official) |
| Deep links | `@capacitor/app` (official) | `tauri-plugin-deep-link` |
| Keyboard / status bar / splash | official plugins | partial, custom Swift |
| Native code to maintain | none | share sheet + keychain as Swift plugins |
| Xcode project | generated, SPM, no CocoaPods | generated by `tauri ios init` |
| App Store documentation | very mature | recent |

The deciding factor is not the UI: both run the same web app at the same
speed. It is **how much native code you have to write and keep alive**. Apple
reviews this app as a packaged web app (guideline 4.2), so the native touches
that get it approved are exactly the ones Tauri does not cover out of the box:
share sheet, haptics, keychain, keyboard handling. With Capacitor they are
official packages maintained by Ionic; with Tauri they would be Swift plugins
written here and maintained here.

The "single codebase" requirement is met at the level that matters: one
`src/`, one test suite, one design system. What is duplicated is packaging
(two thin shells), not product code.

## Consequences

- Two native projects to keep building: `src-tauri/` (desktop) and `ios/`
  (mobile). Both read the same version and the same bundle id.
- The bundle id is duplicated in three places
  (`src-tauri/tauri.conf.json`, `capacitor.config.json`,
  `ios/App/App.xcodeproj`). `scripts/rename-app.mjs` updates all of them at
  once; the id is permanent after the first upload.
- Anything that must exist natively (widget, App Intents, push) will be Swift
  in `ios/`. That is the same work Tauri would require.
- The desktop keeps the self-updater; iOS updates go through the App Store by
  definition, and Mac App Store builds (`VITE_APP_STORE=1`) hide it.

## Rejected alternative

**Tauri 2 iOS.** Attractive on paper (one config system, one plugin registry,
the Rust core reused), but it would have meant writing and maintaining Swift
for the share sheet and the keychain, the two pieces this app needs on every
export and on every login. The saved duplication is a shell, not product code.
